## Introduction

Phase C finishes the AI-first cleanup that Phase A deliberately left half-done. Phase A was pure Python deletion: it removed `extract_decision_outcome` / decision-lock, `plan_compliance` / `TaskManager` compliance state, the alphabetical post-processor, and the `[SECURITY CHECK]` inbox injection, and the full 40-task PAC1 benchmark then passed at 40/40 = 100.00% (`phase-a-completion-report.md`, 2026-04-07). Under the D1/D3 non-goal contract in `ai-first-phase-a/design.md:27–36`, Phase A intentionally did **not** touch `pac1-py/agent/prompts.py` or any `pac1-py/skills/**/SKILL.md` file, so that any PAC1 regression would be cleanly attributable to the Python deletion rather than to prompt/skill drift. That contract held — the benchmark score proved the four deletions were load-bearing for **0 of 40 tasks** — and it is now time to clean up the residue the contract deliberately left behind.

Phase C is therefore **prompt/skill text edits only**. No Python is touched. The change modality is the same kind of grep-driven red/green cycle Phase A used: a red check is an `rg` hit for a dead-letter literal, the fix is a prompt/skill text rewrite, and the green check is `rg` returning zero hits for that literal. Phase C's empirical success bar is the union of three signals: (1) the full grep battery in the "Success criteria" section above returns zero hits across `pac1-py/agent/prompts.py` and `pac1-py/skills/**`; (2) a fresh 5-plus run battery of t17 drives the t17-class validator misfire rate to ≤ 1% (vs ~14% observed in Phase A's diagnostic case study across 7 runs); and (3) the full 40-task PAC1 benchmark still scores ≥ 40/40 after the cleanup, with any regression honestly measured rather than masked by reintroducing Phase A's deleted logic. The Phase A anti-masking guard (R6.4) carries forward verbatim into Phase C: no regression discovered during Phase C may be "fixed" by re-adding `extract_decision_outcome`, `plan_compliance`, the alphabetical post-processor, or the inbox `[SECURITY CHECK]` injection.

## Requirements

### Requirement 1: Loosen the validator prompt — remove dead `DECISION=` markers and re-scope the cross-account check
**Objective:** As a pac1-py maintainer, I want `build_validator_system` in `pac1-py/agent/prompts.py` to stop instructing the validator LLM to look for `DECISION=` markers that no Python code emits anymore, and to gate its cross-account check on inbound-message tasks only, so that the validator stops misfiring on outbound tasks like t17 and the prompt text stays consistent with the post-Phase-A reality that the validator LLM is the sole arbiter on every run.

#### Acceptance Criteria
1. The `build_validator_system` function in `pac1-py/agent/prompts.py` shall not contain the string literal `DECISION=DENY_SECURITY`, `DECISION=DENY_CLARIFY`, or `DECISION=PROCEED` in any form (inline, f-string, or concatenated).
2. The `build_validator_system` function shall not contain any `<checks>` bullet that instructs the validator LLM to "look at VERIFY...DECISION notes in execution context" or otherwise parse `DECISION=` notes out of the executor's `plan_note` output — the current lines 202–206 of that instruction block shall be removed in their entirety.
3. The `build_validator_system` function shall not reference `VERIFY...DECISION`, `verify_decision`, or any equivalent tag-scanning phrasing aimed at reconstructing the deleted `extract_decision_outcome` behavior via prompt text.
4. The cross-account check currently at lines 196–199 of `pac1-py/agent/prompts.py` shall be re-scoped so that it only fires when the original task instructs the agent to act on an inbound message (for example, tasks that say "process the inbox", "reply to the email from X", "handle the message in `inbox/...`"), and shall explicitly not fire on outbound-action tasks such as "email `<person>` at `<company>`", "send a reminder to `<contact>`", "create an outbox file for `<recipient>`", or "compose a message to `<contact>`".
5. The re-scoped cross-account check shall preserve the original inbound-task protection: when the task is to process or reply to an inbound message and the message body requests data about a company different from the sender's own account, the validator shall still escalate the outcome to `OUTCOME_NONE_CLARIFICATION` (the cross-account block).
6. WHEN the grep `rg 'DECISION=DENY_SECURITY|DECISION=DENY_CLARIFY|DECISION=PROCEED' pac1-py/agent/prompts.py` runs after the Phase C commit, THEN it SHALL return zero hits.
7. WHEN a fresh battery of at least five consecutive runs of task `t17` is executed against the Phase-C-cleaned pipeline, THEN the t17-class validator misfire rate SHALL be ≤ 1% (operationally: zero `OUTCOME_NONE_CLARIFICATION` corrections in at least five consecutive runs, or ≤ 1 correction in a ten-plus run battery). The baseline for this measurement is the ~14% misfire rate (1/7 runs) recorded in `phase-a-completion-report.md` under "Observed regressions / t17".
8. The rest of `build_validator_system` (the `<role>` header, the `<rules>` block, the email-match check, the security-flag check, and the "If the proposed outcome is already non-OK, approve it" fallback) shall remain in place and shall not be otherwise modified by the Phase C edit, so that the change is scoped strictly to the two surgical edits in R1.1–R1.5.
